# 指定ビット幅と符号設定に応じた十六進出力

## 指摘

6ビット指定で `FF` を入力したとき、signedでもunsignedでも十六進出力を `3F` にしてよいのか。確認の結果、利用者は「値を保ったまま十六進数の桁境界まで拡張し、signedの負数は符号拡張、unsignedと非負の値はゼロ拡張する」動作を選択した。

## 確認した実装

統合前の `HexToHexStrategy.convert` は入力文字列をそのまま返していた。`HexToBinaryStrategy.convert` は全桁を二進数に展開し、指定したビット数だけ下位側から取り出していた。

現在の `convertFixedPoint` は、二進入力でも十六進入力でも指定幅のビット列を作る。十六進出力では、そのビット列の先頭が `1` かつsignedなら、最上位の4ビット未満のまとまりを `1` で埋める。それ以外は `0` で埋める。入力欄の文字列と、二進出力のビット幅は保持する。

## 判断の基準と複数の観点

6ビットのビット列そのものの十六進表記なら、signedでも `111111` を `3F` と表すことはできる。しかし、値を保って8ビットへ拡張する場合、小数部0ビットのsignedの `111111` は−1なので、`11111111`、すなわち `FF` にする必要がある。符号拡張は上位に符号ビットを補い、値を維持する操作である。[MathWorksの説明](https://www.mathworks.com/help/fixedpoint/ug/guard-bits.html)

今回は後者の仕様が選択されたため、入力文字列の単純な再表示も、一律のゼロ埋めも適さない。符号設定と指定幅内の符号ビットから、出力に補うビットを決める。

## 判定

**Claim is valid — 選択された仕様では、一律に `3F` とするのは不適切。** 6ビットの `111111` は、signedでは `FF`、unsignedでは `3F` を出力する。

## 対応と検証

`src/utils/convertFixedPoint.ts` の十六進変換に符号設定を渡し、両入力形式で同じ変換を使うよう修正した。出力は大文字とし、指定幅に必要な先頭ゼロを保持する。数値計算は指定幅のビット列から行う。

`tests/utils/convertFixedPoint.test.ts` は1〜8ビットの全ビットパターン・全小数部幅・両符号設定について、二進入力、拡張前の十六進入力、拡張後の十六進入力から同じ結果になることを確認する。6ビットの境界値、54ビットと65ビットの出力、小文字入力も検証する。

`tests/App.test.tsx` は、入力欄の文字列を保持しながら、符号設定の切り替えによって十六進出力と数値出力が変わることを確認する。

修正前に回帰テストが失敗することを確認した。修正後は全140件のテスト、lint、ビルドが成功した。lintには既存のルール廃止予定の通知があるが、設定は変更していない。
