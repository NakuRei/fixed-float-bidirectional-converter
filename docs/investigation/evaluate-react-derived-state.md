App の結果とエラーを入力から算出する提案の評価

2026-10-02 時点の実装を確認した。判定は **Claim is valid（指摘は妥当）**。App の結果とエラーは現在の入力から同期的に算出できるため、専用の state と同期用 Effect をなくす方針が適切である。「React は入力だけを state に持つ」という表現は、この App の変換処理に対象を限定して読む必要がある。

**指摘の要約**

`src/App.tsx:50` の Effect で入力から結果・エラーを計算して state に保存する構造をやめ、レンダー時に算出する提案。React 公式の推奨に沿い、状態の追跡を簡単にすることが目的とされている。

**現在の実装**

- `src/App.tsx:24` からの 5 つの state は、整数部ビット数の文字列、小数部ビット数の文字列、符号の有無、入力形式、変換対象の文字列である。
- `src/App.tsx:29` からの `result` と `error` は、上記 5 入力を依存配列に持つ Effect だけが更新する。入力が空なら両方 `null`、成功なら結果と `error: null`、例外なら `result: null` とエラーメッセージになる。
- `src/utils/converters/Converters.ts:21` の変換は同期処理である。呼び先の BinaryConverter、HexConverter、各 Strategy、検証関数、文字列操作も確認した。App が使用する変換経路には通信、DOM 操作、共有状態の書き換えがなく、同じ入力から同じ結果または検証エラーが得られる。コンバーターには `setStrategy` があるが、アプリケーションコードからの呼び出しはない。
- 結果とエラーの表示コンポーネントは受け取った props を表示する。過去の変換結果を保持したり、変換ボタンで確定した結果だけを表示したりする処理はない。
- インストール済みの React と React DOM は 19.3.0。`src/main.tsx` は StrictMode を使う。

**公式の推奨**

React 公式は、既存の props や state から算出できる表示用データはレンダー時に計算するよう説明している。Effect で state を更新すると、古い算出値を使ったレンダーの後に更新が発生する。この App の Effect は、その不要な同期の例に当てはまる。[You Might Not Need an Effect](https://react.dev/learn/you-might-not-need-an-effect#updating-state-based-on-props-or-state)

**複数の観点からの評価**

妥当な点は、同じ情報を入力と算出結果の両方に保持する必要がなくなることである。現状は入力更新後に以前の結果・エラーを使ってレンダーし、Effect 内の state 更新で追従する。レンダー時に計算すれば、入力と結果を同じ入力値の組から作れる。成功時は変換が新しい結果オブジェクトを返すため、現在の Effect は追加の更新を生む。ただし、これだけで利用者に見えるちらつきや重大な不具合が発生しているとは断定しない。

既存コードも成功・失敗・空入力ごとに両方の state を更新しており、最終的な整合性を保つ処理はある。したがって、評価の中心は状態管理の簡素化と不要な更新の削減であり、未確認のユーザー障害を根拠にするものではない。

「入力だけを state に持つ」は React 全般の規則としては広すぎる。`src/components/CustomDropdown.tsx:22` の開閉状態は変換入力だけでは決まらないため、独立した state が必要である。また、`src/hooks/useOutsideClick.ts:7` の Effect は DOM イベントの購読と解除を担う。今回の提案を理由に削除する対象ではない。

算出処理をレンダー時に移すと、入力以外の理由で App が再レンダーされた場合も再計算する。計算コストは未計測であり、常に軽いとは断定しない。まず直接計算し、必要性を計測できた場合に `useMemo` を検討する。メモ化しても入力変更時の計算自体は必要になる。[You Might Not Need an Effect](https://react.dev/learn/you-might-not-need-an-effect#caching-expensive-calculations)

**判定と理由**

**Claim is valid**。現行の結果・エラーには独立した履歴や非同期処理の状態がなく、5 入力と固定された変換処理から導出できる。同期をやめて導出する変更は、この実装について確認できた事実に基づいている。

**推奨する次の変更**

App に入力の state を残し、空入力の分岐、コンバーターの選択、数値への変換、例外のメッセージ化を含む計算から `{ result, error }` を得る。計算部分は JSX の生成と分け、setter を呼ばない。結果とエラーの state および App の Effect を削除する。イベントハンドラーごとに変換処理を分散させる必要はない。

入力ビット数を文字列として保持する挙動、入力を空にできること、変換成功時のエラー解除、失敗時の結果解除を維持する。既存コンバーターの API や検証規則の変更はこの提案には不要である。変更時は空入力、成功から失敗、失敗から成功、入力のクリア、符号・形式・ビット数の変更後の表示を検証する。レンダー回数や Hook の使用自体をテストの仕様にしない。
