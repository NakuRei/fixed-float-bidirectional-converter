標準フォーム部品への置き換え提案の評価

2026年10月3日の修正前の実装を対象に、入力形式の独自ドロップダウンを `select` に置き換え、ラベル・選択値・入力エラーを関連付ける提案を検証した。以下の評価と再考は修正前の記録であり、実装後の確認結果は末尾に記載する。

判定は **Claim is valid（提案は妥当）**。入力形式は Binary と Hexadecimal の単一選択であり、現行コードにはラベルの参照切れと状態の意味付けの不足がある。`select` への置き換えと入力エラーの関連付けを推奨する。ただし、標準部品の採用だけで任意のエージェントによる操作成功が保証されるとは判断しない。

**提案の要約**

独自ドロップダウンを標準の `select` に置き換え、ラベル・選択値・入力エラーを関連付けることで、エージェントが画面の意味と状態を読み取れるようにする提案。評価の対象は、この画面における変更の必要性と方法の妥当性である。

**現在の実装**

- `src/App.tsx:129` の `label htmlFor="inputType"` に対応する `id` は、`CustomDropdown` の出力に存在しない。
- `src/components/CustomDropdown.tsx:52` は現在値の文字列を表示する `button`。開閉状態の `aria-expanded` や選択部品としての意味付けはない。
- `src/components/CustomDropdown.tsx:96` の選択肢は `menu` / `menuitem`。`aria-labelledby="options-menu"` の参照先はなく、選択中の項目を示す属性もない。
- `src/components/CustomDropdown.tsx` と `src/hooks/useOutsideClick.ts` はクリックによる開閉・選択を実装するが、矢印キー、Escape、選択後のフォーカス復帰を実装していない。ネイティブのボタンなので、キーボード操作が一切できないという指摘にはしない。
- `src/components/CustomInput.tsx:30` は標準の `input`。整数部・小数部ビット数と変換値のラベルは `id` と結び付いている。
- `src/components/CustomToggle.tsx:32` は標準の `input type="checkbox"` で、ラベルと checked 状態がある。
- `src/components/ErrorDisplay.tsx:9` はテキストの表示のみ。エラーの ID、入力との関連付け、動的通知の指定はない。`CustomInput` にも `aria-invalid` / `aria-describedby` はない。
- `src/utils/convertFixedPoint.ts:14` の invalid 結果は message のみ。文字列の形式、個別ビット数、ビット数の合計に関するエラーがあり、すべてを変換値入力だけに関連付けるのは正確ではない。

独自ドロップダウンのスタイル指定から、ボタンと選択肢の見た目を画面全体の配色に揃える意図が推測できる。ただし、検索、自由入力、複数選択、複雑な選択肢の表示は実装されていない。

**公式資料との照合**

W3C WAI は、ラベルを明示的に関連付ける場合は `for` と操作部品の `id` を一致させるよう説明している。現在の Input Type の構造はこの関連付けが成立していない。[Labeling Controls](https://www.w3.org/WAI/tutorials/forms/labels/)

WAI-ARIA APG は、combobox / listbox が名前と値を区別して伝えられることと、menu button には値がなく閉じた状態の選択値を伝える用途に向かないことを説明している。独自実装を採用するなら、開閉・選択状態に加えてキーボードとフォーカスの動作も実装する必要がある。[Combobox Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/combobox/)

エラーの状態と説明を結び付ける実装例として、W3C は `aria-invalid` と `aria-describedby` を示している。検証前に `aria-invalid="true"` を設定せず、無効な状態が解消したら解除する。これは WCAG を満たす手法の一例であり、この属性がないという一点だけで WCAG 違反を断定するものではない。[ARIA21](https://www.w3.org/WAI/WCAG22/Techniques/aria/ARIA21)

W3C は、独自部品が必要な場合も機能に合う既存の HTML 要素を基礎にし、適切な要素がないときに WAI-ARIA を使う方針を説明している。今回の二つの値から選ぶ機能には標準の `select` が適合すると判断する。[Custom Controls](https://www.w3.org/WAI/tutorials/forms/custom-controls/)

Playwright は、ラベルで特定した `select` の選択肢を値または表示名で選ぶ `selectOption` を提供している。標準部品とラベルの関連付けを採用すれば、この操作を利用できる。特定のエージェントが同じ方法を使うことや操作の成功率までは、この資料から判断しない。[Actions](https://playwright.dev/docs/input#select-options)

W3C はページ遷移なしでエラーを表示する場合の通知も説明している。入力との関連付けと、表示の変化を通知する仕組みは別であり、リアルタイム変換での通知頻度も含めて検討する必要がある。[User Notification](https://www.w3.org/WAI/tutorials/forms/notifications/)

**複数の観点からの評価**

アクセシビリティの観点では、現在の Input Type のラベルは表示されるだけで、操作部品の名前として関連付けられていない。現在値はボタンの文字として読めるが、入力項目の名前と選択値を区別した構造にはなっていない。これはエージェント利用の有無にかかわらず改善する価値がある。

実装と保守の観点では、この部品の契約は文字列の候補から一つの値を選ぶことであり、標準の `select` と合致する。独自部品に属性だけ追加しても、キーボード操作やフォーカス管理は別に実装する必要がある。ブラウザーが備える選択部品を使う方が、同じ要求を少ない独自処理で満たせる。利用箇所が一つしかないことではなく、必要な機能に標準部品が合っていることが主な理由である。

独自部品自体が不適切という一般論にはしない。必要な意味付けと操作を備えた combobox も選択肢になり、W3C にもそのパターンがある。しかし、このコードに標準部品では満たせない機能は見当たらない。標準部品に変える際の主なトレードオフはポップアップの見た目と操作感がブラウザーや OS に依存する点であり、現在と同じ外観を前提にはできない。

自動操作の観点では、ラベルと役割から操作対象を特定し、標準の選択操作を使えるようになることが利点である。ただし、現在の部品もボタンと項目名を指定すればクリックでき、既存テストもその方法で形式を切り替えている。「今はエージェントで操作不能」「標準部品ならすべてのエージェントで確実」という両方の断定を避ける。特定のエージェントの認識方式、対象ブラウザー、実際の成功率はこの調査では確認していない。

**判定と理由**

**Claim is valid**。壊れているラベルの関連付け、選択・開閉状態の不足、エラーの関連付けの不足はコードと描画した DOM の両方で確認できた。入力形式の選択を標準部品に任せる方針も現行機能に適合する。結論が外部条件によって逆転する状況ではないため、Context-dependent にはしない。「確実に読み取れる」は「意味と状態を標準的な方法で公開し、読み取りや操作の曖昧さを減らす」と表現するのが正確である。

**推奨する次の変更**

1. 入力形式を `select id="inputType"` と `option` で実装し、既存の Input Type ラベルと結び付ける。現在値は React の入力状態から `value` として渡す。標準部品に同じ意味の `role` や `aria-selected` を重ねて独自管理する必要はない。
2. エラー表示に ID を設け、該当する入力から `aria-describedby` で参照する。無効な入力には `aria-invalid` を設定し、成功または空入力によってエラーが消えるときは関連付けと無効状態も解除する。
3. エラーの対象は検証処理で特定し、表示側へ最小限の情報として渡す。例えば文字の形式・長さのエラーは変換値入力、個別のビット数の不備は該当するビット数入力、合計ビット数の不備はビット数の組に関係する。現在のエラーメッセージの文言から対象を逆算したり、全エラーを変換値入力に付けたりしない。
4. 動的なエラー通知も検討する場合、入力との関連付けとは分けて扱う。入力のたびに計算する画面なので、すべての中間エラーを強い通知で読み上げる設計は避け、通知タイミングと読み上げの頻度を確認する。

既存の `CustomInput` と `CustomToggle` は標準の入力要素を使っているため、コンポーネント名が Custom であることを理由に置き換える必要はない。この改善のために送信ボタンや `form` による送信処理を新設する必要もない。修正後は、入力形式の名前と現在値による取得、形式変更後の変換結果、エラーと該当入力の関連付け、訂正・クリア後のエラー状態の解除を検証する。キーボード操作は実ブラウザーでも確認する。

**検証状況**

- `npm test` を実行し、既存の 5 ファイル・140 テストがすべて成功した。既存テストは変換結果やエラー文の表示を確認するが、今回のラベルやエラー関連付けの欠落は検出しない。
- 一時的な Vitest / Testing Library の調査用テスト 5 件で、既存の入力ラベルと checkbox の状態、Input Type の `label.control` が null であること、menu の名前の参照切れと選択状態の欠落、ArrowDown / Escape のキーイベントへの応答不足、不正入力とエラー説明の関連付けの欠落を確認した。5 件すべてが現状を再現した。
- この調査用テストは現状の欠陥を仕様として固定しないよう削除した。確認環境は jsdom であり、実ブラウザーのアクセシビリティツリー、スクリーンリーダーの読み上げ、OS 標準のキー動作、特定エージェントでの操作成功率は未検証である。
- アプリケーションコードと既存テストは変更していない。追加した成果物はこの調査レポートのみである。

**修正方針の再考**

初めて使う人やエージェントが入力から訂正まで操作する観点で再確認すると、標準の選択部品と ARIA 属性の追加に加えて、入力値と操作対象の識別にも修正が必要である。

- `src/App.tsx:33` と `src/App.tsx:42` のビット数の変更処理は、数字以外を含む入力を state に取り込まない。例えば有効な変換結果の表示中に `1.5` を貼り付けても、その値は検証処理に届かず、以前のビット数のままになる。入力文字列をそのまま保持し、既存の `readBitCount` に検証を集約する案に改める。React 公式も、制御された入力の値を変更するには onChange で対応する値を更新する必要があると説明している。[React input](https://react.dev/reference/react-dom/components/input)
- `src/App.tsx:123` の符号設定は、checked 状態によってラベル自体が Signed と Unsigned に変わる。設定項目の名前を固定し、状態は checkbox の checked から取得できるようにする方が、同じ操作対象を再び特定しやすいと判断する。
- `src/App.tsx:159` の変換値は、十六進数の選択中も `inputMode="numeric"` が指定される。HTML Standard では numeric は数値入力用、text は文字入力用の仮想キーボードを示す。この属性は入力機構へのヒントであり、文字の検証ではない。二進数は numeric、十六進数は text とする案に改める。実端末のキーボード表示は未検証である。[HTML Standard inputmode](https://html.spec.whatwg.org/multipage/interaction.html#attr-inputmode)

この再考を踏まえた修正案は以下のとおり。

1. 入力形式には標準の select を使い、独自の開閉・項目選択・外側クリックの処理を取り除く。
2. 入力された文字列をそのまま保持し、ビット数の妥当性は変換処理で判定する。UI の正規表現による入力拒否を除去することで、入力と検証の二重管理を減らす。
3. 操作対象の名前を安定させる。符号設定のラベルは Signed (two's complement) に固定し、状態は checked で示す。変換値のラベルも固定し、二進数・十六進数の文字や接頭辞の制約は入力に関連付けた説明で示す。Integer Bits には、符号付きの場合に符号ビットを含むことを説明する。
4. invalid 結果に、変換関数の入力項目を識別する invalidFields を持たせる案は維持する。これは文字列メッセージにはない構造化された情報であり、React の追加 state ではない。検証結果から入力の無効状態とエラーへの参照を算出する。
5. CustomInput は、標準 input の属性を受け渡し、共有スタイルを付ける薄い部品にする。必要な制御用 props の型を保ちつつ標準属性の型を利用し、ARIA 属性ごとに独自の対応を追加し続ける構造を避ける。

受け入れ確認は属性の有無だけでなく、操作を通した結果で行う。例えば整数部・小数部を各 4 ビットとして十六進数 CD を入力し、符号付きの -3.1875 と符号なしの 12.8125 を同じ設定項目で切り替えられることを確認する。次に整数部へ 1.5 を入力すると、その入力が残ったまま当該欄のエラーになり、古い変換結果が消えること、4 に訂正すると結果が再び得られることを確認する。これは修正後に検証する条件であり、修正済みの挙動として報告するものではない。

再考の段階ではアプリケーションコードとテストを変更していない。

**実装後の確認結果**

承認された方針に基づいて実装した。入力形式を標準の select に置き換え、CustomDropdown と専用の useOutsideClick を削除した。符号設定と変換値のラベルを固定し、形式ごとの入力説明と inputMode を設定した。ビット数の変更処理は入力をそのまま保存し、検証は convertFixedPoint に集約した。

invalid 結果には入力項目を表す invalidFields を追加した。App がこの情報から入力の無効状態とエラー参照を算出し、CustomInput は標準 input の属性を渡す。成功・入力クリア時の参照解除と、元の入力説明の保持も確認した。追加の React state は設けていない。

既存の変換結果に関する検証を維持し、入力ラベル・選択状態・エラー対象・不正入力の保持と訂正のテストを追加した。npm test は6ファイル・155件が成功し、npm run lint と npm run build も成功した。lint には既存の jsx-sort-props ルールに関する非推奨通知が出るが、検査エラーはない。

Chromium でもキーボード操作、CD の符号切替、不正ビット数 1.5 の入力、4 への訂正、合計ビット数のエラー、入力クリアを確認した。3種類の画面幅とエラー・結果表示の確認内容は [UI review report](../../ui-review-report.md) に記録した。

**再点検後の修正**

ビット列が空の場合にビット数の検証も省略されるため、1.5 などの未修正のビット数が残っていても、ビット列の消去によってエラーと入力の無効状態が解除されていた。初回のテストもこの挙動を期待していた。利用者の了承を得て、個別のビット数と合計の検証を、ビット列の空判定より先に行うよう修正した。

ビット数のエラーは、ビット列が未入力のときも表示し、ビット数が訂正されるまで保持する。ビット数が有効でビット列が空なら、エラーも変換結果も表示しない。UI に検証処理や状態は追加せず、既存の検証結果と入力の関連付けを使う。

単体・DOM テストで、整数部・小数部それぞれの不正、複数欄の不正、合計ビット数の不正、未入力時の検証、ビット列消去後の保持、訂正後の解除を確認した。修正前には該当する10ケースが失敗し、修正後は npm test の6ファイル・164件すべてが成功した。npm run lint と npm run build も成功した。
